# Story 2.3: Primeira experiência visual do vendedor

## Status

**Done** — QA Gate PASS em 2026-09-16 para a primeira experiência visual local. Sem push ou deploy; não representa aprovação do MVP completo para piloto.

ClickUp: [86e3a4v5j](https://app.clickup.com/t/86e3a4v5j), Epic 2 `86e39g7q3`, lista Backlog `901716946800`.

## Story

Como Vendedor, quero entrar no aplicativo e consultar/reordenar minha rota publicada por uma interface clara no celular, para avaliar o primeiro fluxo visual do produto com dados sintéticos reais do backend.

## Acceptance Criteria

1. Login em `/login` com e-mail/senha, rótulos acessíveis, mostrar/ocultar senha, estado de envio e erro genérico. Usa Supabase Auth existente, valida perfil ativo e capacidade de vendedor antes de concluir; não retorna tokens no JSON nem os persiste em localStorage. Recuperação é orientação ao administrador nesta demonstração, sem simular envio de e-mail. [Source: Docs/prd.md#fr-001; #34-core-screens-and-views; Docs/architecture.md#10-arquitetura-frontend; #15-segurança-e-desempenho]
2. Sessão por cookies same-origin; login/logout exigem Origin e cabeçalho CSRF, rejeitam Bearer misturado, usam limites de corpo/no-store e mensagens sem credenciais. Logout encerra a sessão local e limpa a tela; refresh/401/403 nunca deixam dados de outro ator visíveis. [Source: Docs/architecture.md#108-comunicação-com-a-api; #109-proteção-de-navegação; #151-segurança]
3. `/route` mostra a rota obtida de `/api/v1/me/routes/today` após `/api/v1/me`: vendedor, data canônica, total e progresso calculados dos estados, nome/endereço, prioridade, ordem e estado de cada parada. Sem sessão, oferece login; sem rota, vazio explícito; indisponibilidade não se apresenta como rota vazia. Shell/HTML/cache não embutem dados privados. [Source: Docs/prd.md#fr-006; #ac-005-consultar-e-reordenar-a-própria-rota; Docs/architecture.md#104-arquitetura-de-rotas; #107-service-worker-e-cache]
4. Reordenar usa controles acessíveis para subir/descer somente pendências, mantendo posições não pendentes. Edição é local transitória até Salvar; permite Cancelar; confirmação vem do PUT já existente e recarga canônica. Conflito 409 exige recarregar explicitamente, sem sobrescrita automática; falhas de conexão preservam o rascunho visual e não anunciam sucesso. [Source: Docs/prd.md#fr-007; Docs/architecture.md#108-comunicação-com-a-api; #1010-formulários-e-validação; Docs/stories/2.2.story.md]
5. Visual mobile-first segue a referência `01_rota_do_dia.png`: verde Cirne/laranja/superfícies claras, cabeçalho de marca, resumo escuro e cartões legíveis; tokens CSS, foco visível, contraste de texto e alvos de pelo menos 44px. Desktop aproveita largura com layout coerente. Não há botões fictícios de visita/mapa/perfil. [Source: Docs/prd.md#3-user-interface-design-goals; Docs/PACOTE_VISUAL_Cirne_Rotas_v0.1/LEIA-ME_REFERENCIAS_VISUAIS.txt]
6. Offline canônico permanece fora deste incremento: UI informa necessidade de conexão para carregar/salvar e não usa o pacote sintético como rota do usuário. A demonstração técnica existente continua em `/demo/offline`, com seus testes de durabilidade; fallback de `/route` não expõe essa fixture. [Source: Docs/architecture.md#106-persistência-e-sincronização-offline; #107-service-worker-e-cache; Docs/stories/2.2.story.md#scope-boundaries]
7. Testes cobrem entrada/saída por cookies, credenciais inválidas, bloqueio/escopo, CSRF, redaction, reordenação, conflito, cancelamento, vazio, falha e viewports móvel/desktop. Login e rota são exercitados contra Supabase local, sem dados reais. Lint/typecheck/unit/build/pgTAP/integração/E2E passam; documentação e evidência visual atualizadas. [Source: Docs/architecture.md#16-estratégia-de-testes; AGENTS.md]

## Scope Boundaries

- Não implementar visita, navegação externa, painel gerencial, recuperação SMTP, cadastro, alteração da composição ou parâmetros fictícios.
- Sem migração de banco. Usar contratos v2 e RPCs já validados.
- O shell de campo continua genérico. Esta story não declara o fluxo inteiro do MVP pronto para piloto.
- Sem novas dependências: estado transitório simples segue o padrão React existente; clientes HTTP tipados ficam em `lib/`, fora dos componentes. A adoção de gestores de estado adicionais permanece para stories que precisem deles.

## Dev Notes

- Fundação existente: `server/identity.ts`, `server/routes/http.ts`, `server/routes/service.ts` e `lib/offline/*`; `/me` valida identidade atual e `/me/routes/today` deriva a data operacional no servidor. [Source: Docs/stories/1.2.story.md; Docs/stories/2.2.story.md]
- Componentes novos em `features/auth` e `features/routes`; acesso HTTP via `lib/` e sessão via adaptador de servidor, mantendo as fronteiras da arquitetura. APIs de sessão sob `/api/v1/auth/session`; usam SDK Auth já instalado, chave publicável e cookies gerenciados no servidor. [Source: Docs/architecture.md#108-comunicação-com-a-api; #11-arquitetura-backend; #12-estrutura-unificada-do-projeto]
- Ler as instruções locais do Next em `node_modules/next/dist/docs` antes de implementar. Sem arquivos arquiteturais shardados: usar `Docs/architecture.md`. [Source: apps/web/AGENTS.md; .aiox-core/core-config.yaml]
- A referência visual orienta hierarquia/paleta; números/nome/data devem vir do backend. Reordenação por botões evita dependência de drag-and-drop e permite teclado. [Source: Docs/prd.md#31-overall-ux-vision; #36-accessibility]
- Testar autenticação pelo endpoint e CLI de diagnóstico existente antes da UI. Sessão HttpOnly é adequada a este recorte porque toda operação autenticada passa pelo BFF; nenhum SDK Auth roda no navegador. [Source: Docs/architecture.md#108-comunicação-com-a-api; #15-segurança-e-desempenho]
