## Story

Como responsável pelo desenvolvimento do Cirne Rotas, quero instalar e executar uma base local reproduzível, verificar sua saúde pela CLI e rodar os quality gates, para desenvolver e testar os próximos fluxos no computador e preparar a futura promoção para uma VPS.

Primeiro incremento do Epic 1, sem dependência de story anterior. O epic completo inclui identidade, autorização, persistência e publicação; esta story entrega apenas a fundação executável. A sequência vem da arquitetura §20.6. O PRD §5.1 contém escopo de alto nível, portanto os critérios abaixo são derivados desse escopo e da arquitetura, não copiados de critérios de story inexistentes.

## Acceptance Criteria

1. **Monorepo reproduzível:** existem `apps/web`, `apps/cli`, `packages/contracts` e `packages/config`, com npm workspaces, TypeScript estrito, lockfile e versões verificadas. `npm ci` instala a partir do lockfile; dependências de funcionalidades futuras não são instaladas sem necessidade. A matriz das versões efetivamente utilizadas e eventuais divergências da arquitetura fica registrada no README. [Source: Docs/architecture.md#3-stack-tecnológica; #12-estrutura-unificada-do-projeto]
2. **Diagnóstico local:** `npm run local:doctor` identifica disponibilidade/versões de Node, npm, WSL2, runtime Docker compatível, Compose e Supabase CLI, além de conflitos nas portas configuradas. Oferece saída humana e `--json`, retorna código diferente de zero quando faltar requisito e não instala nem altera ferramentas implicitamente. Nenhuma saída contém valores de segredos. [Source: Docs/architecture.md#13-fluxo-de-desenvolvimento-local]
3. **Serviços isolados:** os comandos `db:start` e `db:stop` iniciam/param o Supabase local com projeto próprio, preservando dados ao parar. A exposição padrão fica em loopback; projeto, volumes, rede e credenciais não dependem do n8n. A configuração pode ser reaplicada sem destruir dados. Somente dados sintéticos são usados. [Source: Docs/architecture.md#132-comandos-previstos; PRD NFR-018]
4. **Canário CLI/API:** `GET /api/v1/health/live` devolve estado mínimo do processo e não consulta Supabase; o comando de diagnóstico HTTP da CLI consome esse endpoint usando contrato compartilhado e falha claramente se a aplicação estiver inacessível ou retornar resposta inválida. Não há dados de negócio, segredos ou configuração na resposta pública. [Source: Docs/architecture.md#192-saúde-diagnóstico-e-comandos; #5-especificação-da-api]
5. **Configuração e logs:** configuração validada impede inicialização com valores obrigatórios inválidos; módulos públicos e privados são separados. Logs JSON contêm correlação, nível, rota-modelo, status e duração quando aplicáveis, com redaction. Arquivos `.env` existentes são preservados e excluídos do contexto da imagem e do Git. [Source: Docs/architecture.md#1112-configuração-e-segredos; #191-sinais-e-privacidade]
6. **Execução de produção local:** `npm run dev`, `npm run build` e `npm run start` funcionam. Dockerfile multi-stage gera runtime não-root com saída standalone, ativos necessários e health check acessível localmente. A imagem inicia sem acesso a dados remotos ou socket Docker. O README mostra como reproduzir o ensaio. [Source: Docs/architecture.md#142-imagem-e-configuração; #13-fluxo-de-desenvolvimento-local]
7. **Quality gates reais:** `npm run lint`, `npm run typecheck`, `npm test` e `npm run build` passam. Testes verificam configuração inválida, redaction, contrato de saúde, dependência ausente e falha HTTP da CLI. CI declarativa executa esses gates com permissões mínimas e Actions fixadas por SHA; sem publicação/deploy automático ou segredos de produção em PR. A execução no GitHub só é declarada validada quando houver evidência remota. [Source: Docs/architecture.md#143-pipeline-e-publicação; #16-estratégia-de-testes; Constitution V]
8. **Operação documentada:** README cobre preparo, configuração de exemplo, iniciar/parar, diagnóstico, testes e imagem. A configuração AIOX aponta para os documentos monolíticos existentes em `Docs/` e para `Docs/stories/`, corrigindo flags de fragmentação incorretas. Repositório Git local e ignore rules estão preparados sem incluir credenciais. Checklist, file list e evidências desta story são atualizados antes da conclusão. [Source: Docs/architecture.md#12-estrutura-unificada-do-projeto; #174-documentação-e-disciplina-por-story]

## Limites e dependências

- Login, `/me`, RLS do domínio, migrações de visitas, outbox, fotos e telas operacionais pertencem aos próximos incrementos do Epic 1 e dos epics seguintes.
- `/health/ready` dependente de banco e canário autenticado serão entregues junto da base de identidade/dados. `live` não comprova que Auth, Storage ou banco funcionam.
- Provisionamento de VPS, domínio, Supabase Cloud, SMTP, registro de imagem remoto e publicação não integram este aceite local. O Epic 1 só termina depois de seus demais incrementos.
- A direção local → VPS foi autorizada na conversa e registrada na arquitetura §2.8. O PRD ainda contém Vercel em NFR-016/DEC-012; reconciliar documentalmente antes da publicação remota, sem bloquear esta base local.
- WSL2/runtime podem exigir instalação e reinicialização da máquina. Identificar a necessidade pelo diagnóstico; não marcar os ensaios de container como passados sem executá-los.
