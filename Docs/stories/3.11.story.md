# Story 3.11: Importação controlada da base de clientes por Excel

## Status

**Done** — implementação e quality gates aprovados com dados sintéticos; uso de dados reais permanece condicionado ao fechamento operacional de `AB-13`.

## Story

Como Gestor autorizado, quero enviar uma planilha Excel para validar e atualizar a base de clientes e suas carteiras, para que os clientes corretos fiquem disponíveis na criação de rotas e a base possa ser atualizada sempre que necessário.

## Contexto e rastreabilidade

- Requisito explícito do usuário: criar tela de upload da base de clientes em Excel e permitir ao Gestor repetir a atualização quando necessário.
- Rastreia `FR-003`, `AC-033`, `DM-18`, `UI-G06` e o contrato “Importar clientes” do PRD. O usuário aprova nesta story a permissão limitada do Gestor prevista na matriz; Administrador mantém a permissão administrativa.
- A entrada continua sendo arquivo controlado, sem integração automática com Orion. A origem oficial, o arquivo real e a política externa de conflito ainda devem ser fornecidos antes de usar dados reais (`AB-13`). Desenvolvimento e testes usam dados sintéticos.
- A Story 3.10 introduziu `api.client_seller_scopes`; a importação precisa manter esses vínculos para a agenda avulsa falhar fechada sem impedir a seleção de clientes para rotas autorizadas.

## Acceptance Criteria

1. Existe uma tela responsiva em `/management/clients` para Gestor ou Administrador com capacidade explícita de importar clientes. Usuário sem a capacidade recebe negação no servidor, mesmo que acesse a URL ou invoque a API diretamente.
2. A tela aceita arquivo `.xlsx`, identifica o arquivo selecionado e oferece duas ações distintas: **Validar** e **Importar**. A validação não altera clientes, carteiras ou lotes definitivos.
3. O sistema disponibiliza um modelo de planilha com cabeçalhos canônicos: `referencia_externa`, `nome`, `endereco`, `latitude`, `longitude`, `referencia_carteira`, `vendedor_email` e `status`. `referencia_externa`, `nome`, `endereco` e `vendedor_email` são obrigatórios; `status` aceita `active` ou `archived` e assume `active` quando vazio.
4. Cada linha é validada de forma independente. O resultado mostra total, aceitas e rejeitadas e, para cada rejeição, número da linha e códigos/mensagens acionáveis, incluindo cabeçalho ausente, campo obrigatório, coordenada inválida, status inválido, referência repetida no arquivo e vendedor inexistente/inativo/sem papel de Vendedor.
5. Células tipadas como fórmula não são executadas nem aceitas como valor de negócio. Em campos textuais, conteúdo iniciado por `=`, `+`, `-` ou `@` é neutralizado/rejeitado de forma segura e nunca é devolvido em exportação de modo que possa executar como fórmula; números negativos válidos continuam permitidos em latitude/longitude.
6. A importação usa `referencia_externa` como chave estável: cria cliente inexistente e atualiza o cliente existente sem duplicá-lo. Mudanças preservam antes/depois, autor autenticado, origem, horário e lote. Conflitos de referência não são resolvidos silenciosamente.
7. Linhas válidas são importadas mesmo quando outras linhas forem rejeitadas; cada linha é aplicada atomicamente com sua auditoria. Contadores e resultado final refletem o que de fato foi persistido, sem deixar uma linha parcialmente aplicada.
8. `vendedor_email` resolve um usuário ativo com papel Vendedor e mantém o vínculo ativo em `api.client_seller_scopes`. Troca de vendedor revoga o vínculo anterior criado/gerido pela importação e cria o novo com autor; vínculos fora do domínio controlado pelo lote não são removidos silenciosamente.
9. Cliente com `status=archived` é inativado e deixa de aparecer para novas rotas e agenda avulsa, mas permanece referenciado no histórico. Cliente omitido do arquivo não é arquivado nem alterado automaticamente.
10. Reenvio do mesmo conteúdo é detectado por checksum. A API não cria duplicidade de lote, cliente, vínculo ou auditoria e retorna o resultado canônico já existente; nome do arquivo diferente não altera a identidade do conteúdo.
11. O sistema persiste `api.import_batches` e `private.import_batch_rows` com origem, checksum, autor, horários, estado, payload sanitizado, resultado e erros. Tabelas privadas não são consultáveis diretamente pelo navegador; leituras usam função/endpoint estreito e autorizado.
12. Após a importação, a tela apresenta resumo e rejeições do lote e permite consultar novamente o resultado por `GET /client-imports/{id}`. A lista de clientes é atualizada e mostra referência, nome, endereço, carteira/vendedor e status, com paginação/limite estável.
13. O fluxo existe primeiro por contratos e CLI: validar e importar uma planilha sintética, repetir o mesmo arquivo e consultar o lote produzem saída JSON estável e exit code significativo, sem expor tokens ou conteúdo sensível desnecessário.
14. Os endpoints previstos são implementados sob `/api/v1`: `GET /clients`, `POST /client-imports/validate`, `POST /client-imports` e `GET /client-imports/{id}`. Respostas usam contratos versionados e envelopes de erro existentes; handlers não contêm SQL ou regras de negócio.
15. Testes cobrem parsing de Excel, fórmulas, validação por linha, autorização de Gestor/Administrador, negação a Vendedor, RLS/grants, criação/atualização/inativação, carteira, sucesso parcial, checksum idempotente, auditoria, CLI e jornada visual. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run db:test` e testes de integração/E2E aplicáveis passam.

## Fora de escopo

- Integração automática, webhook ou sincronização direta com Orion.
- Geocodificação automática, correção postal ou enriquecimento externo.
- Arquivamento de clientes apenas porque não constam no arquivo.
- Exclusão física de clientes, histórico, lotes ou vínculos usados por rotas/visitas.
- Uso de arquivo real antes do fechamento operacional de `AB-13` e dos gates de dados reais.

## Dev Notes

### Previous Story Insights

- `api.client_seller_scopes` é a fonte explícita de autorização da carteira para operações avulsas e falha fechada sem vínculo; a importação futura foi registrada como mantenedora controlada dessa relação. [Source: `Docs/stories/3.10.story.md#completion-notes-list`]
- Clientes e registros históricos não devem ser removidos em cascata; inativação preserva referências existentes. [Source: `Docs/architecture.md#93-catálogo-físico`]

### Data Models

- `Client` contém `externalReference`, `name`, `address`, coordenadas decimais opcionais, `portfolioReference` e `status`. [Source: `Docs/architecture.md#42-identidade-e-clientes`]
- `api.clients.external_reference` é única quando informada; `created_from_import_batch_id` e `archived_at` preservam procedência/estado. [Source: `Docs/architecture.md#93-catálogo-físico`]
- `api.import_batches` guarda origem, checksum, autor, status, contadores e conclusão; `private.import_batch_rows` guarda número, payload, estado e códigos de erro por lote. [Source: `Docs/architecture.md#93-catálogo-físico`]
- `api.client_seller_scopes` possui vínculo ativo único por cliente/vendedor e autoriza operações avulsas fora da rota. [Source: `Docs/architecture.md#93-catálogo-físico`]

### API and Security

- A arquitetura prevê `GET /clients`, `POST /client-imports/validate`, `POST /client-imports`, `GET /client-imports/{id}` e `PATCH /clients/{id}`; esta story implementa os quatro endpoints necessários ao upload/listagem e não inclui correção manual separada. [Source: `Docs/architecture.md#52-superfície-da-api`]
- Tabelas `private` não têm acesso direto de `anon`/`authenticated`; funções `SECURITY DEFINER` usam `search_path` vazio e grants explícitos. [Source: `Docs/architecture.md#97-rls-e-superfície-de-escrita`]
- Importações neutralizam fórmulas; texto é renderizado sem HTML arbitrário; credenciais privilegiadas nunca chegam ao navegador. [Source: `Docs/architecture.md#152-fronteiras-http-csp-e-validação`]
- Orion não possui integração automática no MVP; a entrada é arquivo controlado. [Source: `Docs/architecture.md#75-integrações-explicitamente-ausentes`]

### UI and File Locations

- Rotas previstas incluem `/management/clients` e `/management/client-imports/[batchId]`; layouts não substituem autorização server-side. [Source: `Docs/architecture.md#104-arquitetura-de-rotas`]
- Handlers ficam em `apps/web/src/app/api/v1/client-imports/` e devem ser adaptadores sem SQL/regra comercial; componentes da feature ficam isolados por módulo. [Source: `Docs/architecture.md#136-fronteiras-de-código`]
- CLI, API e UI reutilizam contratos compartilhados; a direção é UI/handler/CLI → casos de uso → domínio/portas. [Source: `Docs/architecture.md#171-regras-críticas`]

### Testing

- Usar Vitest para contratos/domínio, pgTAP para constraints/RLS/funções, integração por processo HTTP real e Playwright para a jornada; fixtures não dependem de rede externa nem de dados reais. [Source: `Docs/architecture.md#16-estratégia-de-testes`]
- Cobrir autorização negativa, idempotência, falha intermediária, concorrência, payload inválido e auditoria. [Source: `Docs/architecture.md#162-cenários-obrigatórios-e-rastreabilidade`]

### Project Structure Notes

- A arquitetura monolítica v4 já prevê os módulos `client-imports`, `clients`, contratos compartilhados, migrações Supabase e rotas de gestão; não há conflito estrutural identificado.
- `AB-13` permanece parcialmente aberto quanto ao arquivo real, fonte oficial, frequência externa e conflitos com Orion. A implementação deve ser validada apenas com planilha sintética até aprovação operacional.
